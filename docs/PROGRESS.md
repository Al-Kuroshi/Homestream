All 6 tasks passed individual spec+quality review. The final whole-branch review (dispatched on the most capable model) caught a real, load-bearing bug the individual task reviews had missed — worth knowing about if you're touching this code:
- **`-hls_time 2` was silently inert.** HLS can only cut segments at keyframes, and libx264's default GOP (~250 frames, ~10s) meant `-hls_time 2` had no effect — segments came out at ~10s, not 2s. This cascaded into three more problems the same bug was masking: the hardcoded 5s startup-detection deadline was actually racing a ~10s encode (would intermittently fail on real hardware even though it passed in CI with a tiny synthetic fixture), the plan's own "growing playlist" Definition-of-Done item was untested (a 6s test fixture produced exactly one segment, so the "wait for a `.ts` file" test was vacuous), and 4 test files' missing `sessions.Close()` calls were only harmless by accident (ffmpeg finished before the test ended, so nothing was still running to race `t.TempDir()`'s cleanup). Fixed by adding `-force_key_frames "expr:gte(t,n_forced*2)"` to force keyframes at the interval `-hls_time` expects, `-preset veryfast`, a configurable `startupTimeout` (default 15s, up from the hardcoded 5s), a rewritten segmentation test that proves real growth (12s fixture, polls for ≥2 segments), and the 4 missing cleanup calls.
- Also fixed in the same pass: transcode session directory was a fixed, unconfigurable path under `os.TempDir()` — now `PERSONALTV_SESSIONS_DIR`-configurable, matching the existing `PERSONALTV_DB_PATH`/`PERSONALTV_PORT` convention (a prerequisite the not-yet-written Docker packaging plan would otherwise have had to retrofit). Two production symbols (`PlaybackServiceForTest`, `StartTestSession`) that existed solely for test access were removed in favor of the test helpers returning the real `*playback.SessionManager` they already construct.
- A design decision worth flagging forward: in `hls` mode, `offset_sec` in the watch response has *already* been applied via ffmpeg's `-ss` seek when the session started — a client must not seek by it again, or it'll double-seek. Documented on `TuneInResult`/`watchResponse`, but there's no client yet to get this wrong (see below) — whoever writes the TV/player UI should read that doc comment first.
- `docs/design/2026-08-23-personal-tv-playback-design.md` §4/§6 are now stale: they still describe a "walk forward and serve the next existing program" behavior that the plan's Global Constraints deliberately overrode with "never skip ahead" (Task 5's `TestTuneIn_DoesNotJumpAheadToAFutureProgramWhenCurrentFileIsMissing` locks in the *opposite* of what the spec's §6 describes testing). The code is correct per the plan; the spec doc itself needs a note added so a future reader doesn't "fix" the code back to match stale prose.

The single most load-bearing non-obvious change in this plan, worth knowing about before touching playback: **`internal/playback/tunein.go`'s Pass B now resolves the schedule via `channels.Service.ResolvedWindow` instead of the old `ListPrograms`.** This was a plan defect caught mid-run, not something the plan asked for — `tunein.go` is production code that no task's file list mentioned. - **Tasks 10 → 11:** a genuine position-computation bug was found in Task 10 and deliberately deferred to Task 11. `handleDrop` computed `insertBeforeIndex` from the pre-move rendered list (which still contains the dragged slot) but excluded the dragged slot from `existingPositions` before calling `positionForInsert`, so on a multi-slot day a forward move landed one position off. Non-destructive and user-recoverable, and Task 11 replaced that whole function anyway, so fixing it twice would have been wasted work. Task 11's `computePosition` carries the corrected version (it finds the excluded slot's own index and decrements `insertBeforeIndex` when that index precedes the insertion point), trace-verified against forward-move, backward-move, and single-occupant cases.
- Also found during the run and worth remembering: `ResolvedWindow` resolves whole calendar days, so a non-midnight `to` bound includes occurrences past the exclusive cutoff (matches the brief; this plan's own callers always pass midnight-aligned week boundaries), and `ResolveDate`'s `sort.Slice` over recurring slots is not stable, so two slots with equal positions tie non-deterministically.

The final whole-branch review (dispatched on the most capable model) found 1 Critical and 8 Important issues, all fixed in one consolidated wave:
- **The new grid had no way to delete a slot.** `useDeleteSlot`/`deleteSlot` were fully implemented and tested but never imported by any screen — a straight regression against the dropdown editor the grid replaced, and this file previously claimed the feature existed. Each block now has a `×` button with its own error banner. This slipped past all 11 task reviews because Task 7's delete-and-recreate scope adjustment never included a "what did the old screen do that the new one must still do" check.
- **Gap slots were invisible or wrong everywhere outside the schedule grid.** `resolvedSlotResponse` and `programStateJSON` carried no `kind`/`gap_label`, and a gap resolves with `media_item_id` 0 — so the Guide rendered a scheduled break as the literal text "Media #0", the TV screen's next-up line said "Up next: Unknown", and worst of all `TuneIn`'s Pass B dropped the gap occurrence in its media lookup and returned `unavailable`, i.e. the error state, for a deliberate correctly-scheduled break. Both responses now carry `kind`/`gap_label`, and `TuneIn` short-circuits an on-air gap to `off_air`, reusing the existing interstitial + next-up countdown.
- **Moving an existing gap destroyed its duration and label.** `PUT /api/slots/{id}` is a full replace, and `confirmPending` sent `gap_duration_sec` from whatever the "new gap" minutes input last held plus a hardcoded `"Gap"` label — so dragging a 30-minute "Ad Break" to a new position silently rewrote it to a 5-minute "Gap". The pending placement now carries the existing gap's own duration and label through the move.
- **Drop targets were 8px tall with `:hover` as their only affordance**, which most browsers suppress during a native HTML5 drag. Now 24px, with a real active state driven by `onDragEnter`/`onDragLeave`.
- **`positionForInsert` returned unrounded fractional positions.** Four inserts at the same boundary give 1500 → 1250 → 1125 → 1062.5, and the API's `position` is a Go `*int` — so that fourth insert failed JSON decoding and surfaced the raw Go decoder error text to the user in the mutation-error banner. The result is now always an integer.
- **`validateSlot`'s recurring branch never checked existing one-off slots.** It only summed that weekday's recurring durations against 24h, while the one-off branch already resolved the full day before checking overlap — so the identical collision was rejected or accepted purely depending on which of the two slots the user happened to create first. The recurring branch now resolves its reflowed chain against every existing one-off whose date falls on the candidate's weekday.
- Plus three documentation fixes: `CLAUDE.md`, the 2026-08-21 design doc, and the PRD all still said this work was "approved, not yet implemented", and `CLAUDE.md`'s domain-model section still taught `Program` rather than `Slot` (it is read by every future agent session, so it now describes recurring/one-off addressing, gap slots, resolution, and the UTC constraint); and this Plan 5 section itself, which previously claimed delete existed and claimed there were no fix rounds.

**Known, accepted limitations of this plan — deliberately deferred, not oversights:**
- **UTC day boundaries vs. locally-rendered clock times.** All day-of-week and midnight arithmetic is UTC (an approved global constraint), but the Guide and TV screens render clock times in the browser's local timezone. For a non-UTC viewer, a slot dropped at the top of the grid's "Mon" column can appear in the Guide as e.g. "Sunday 19:00" — the same slot, two different answers on two screens. The grid now labels itself "(all times UTC)" so this is disclosed rather than discovered, but it is a real rough edge for anyone not on UTC and would need a proper timezone-handling design to actually resolve.
- **Mixed recurring/one-off days confuse the drag position math.** `computePosition` (`ChannelScheduleScreen.tsx`) only ever considers a day's *recurring* siblings when computing a sparse position, while `slotsForDate` renders recurring and one-off occurrences interleaved. On a day that mixes both, the drop index and the position index therefore address different lists, and a slot can land one position off from where it was dropped. Non-destructive and user-recoverable by re-dragging, but real. Reconciling the two addressing schemes is its own piece of design work.
- Smaller parked follow-ups from the final review, none blocking: `ResolveDate`'s non-stable sort tie-breaking; an unused DB index; no items-map memoization in `tunein.go`; `day_of_week` range never bounds-checked server-side; `ResolvedWindow`'s doc comment describes `to` as exclusive when whole-day resolution makes it effectively inclusive; `program_id` is now a misleading name for what is a slot ID (it survives in `scheduler.ScheduledProgram` and both JSON responses); `MutationError` doesn't span the grid's columns; no input for a gap's label when creating one (always "Gap" — only preserved, never edited); no time-of-day text on grid blocks; the slots query's loading state isn't gated separately; no end-to-end integration test for a recurring schedule; the gap-minutes input doesn't reset between separate placements; and `TestService_CurrentState_NoPrograms` kept its pre-`Slot` name.

## Key decisions made (see the design specs for full reasoning)

- **Backend:** Go, single static binary, `modernc.org/sqlite` (pure-Go, no CGO).
- **Frontend:** React + TypeScript SPA (Vite), embedded into the Go binary via `go:embed`. Plain CSS (no UI framework), React Router, TanStack Query, Vitest/RTL/MSW for testing. See the frontend design spec for the full rationale (persistent sidebar nav, timeline-grid Guide over a simpler now/next list, Settings scoped to media sources only). Its "no drag-and-drop scheduling" decision is now superseded — see the recurring slot-chain scheduling design spec below.
- **Database:** SQLite behind repository interfaces, swappable to PostgreSQL later without touching business logic.
- **Media source (MVP):** local filesystem only, including NAS/network shares via a Docker bind mount.
- **Metadata/subtitles:** no internet enrichment in MVP — filename + `ffprobe` technical metadata only.
- **Scheduling:** pure function of `(schedule, wall clock)`, recomputed on demand — no background ticking process, nothing lost on restart. Off-air gaps between programs are a first-class state, not an error, on both backend and frontend.
- **Media scanning:** manual rescan only for MVP, no filesystem watcher.
